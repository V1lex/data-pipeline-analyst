# data-pipeline-analyst

**AI Data Pipeline Analyst** — интеллектуальная система, которая преобразует бизнес-требования на естественном языке в строгие декларативные спецификации конвейеров обработки данных, выполняет их математическую верификацию с помощью **TLA+/TLC** и подготавливает структуру для генерации кода на **PySpark**.

---

## 2. Реализованные задачи (Т11 – Т15)

### [Т11] Единый JSON-контракт, Pydantic-модели и валидация DAG (`pipeline_spec/`)
* **10 поддерживаемых операций MVP**: `read`, `filter`, `select`, `with_columns`, `join`, `aggregate`, `deduplicate`, `sort`, `union`, `write`.
* Дерево выражений AST: арифметика (`add`, `sub`, `mul`, `div`), сравнения (`eq`, `ne`, `lt`, `gt`, `between`), логика (`and`, `or`, `not`), условные конструкции `when/otherwise`, приведение типов `cast` и вызовы функций (`coalesce`, `concat`, `trim`, `lower`).
* Модель `PipelineSpecification`: строгая проверка уникальности всех идентификаторов, валидация отсутствия циклических зависимостей в графе (алгоритм Кана с методом `get_topological_order()`).
* Секция `formal_model`: конечный автомат конвейера (переменные, переходы, инварианты, отсутствие тупиков), совместимый с TLA+ компилятором.
* Эталонная спецификация: `pipeline_spec/examples/e_commerce_orders_pipeline.json` и документация контракта в `pipeline_spec/docs/pipeline_specification_contract.md`.

### [Т12] Интеграция с Gemini API, системные промпты и сессионный контекст (`analyst/`)
* Подключение к Google Gemini API (модель `gemini-3.5-flash-lite`) через официальный SDK `google-genai` со Structured Outputs.
* Сессионный менеджер `AnalystSession` сохраняет историю реплик и обогащает контекст диалога.
* Системная инструкция запрещает агенту молча додумывать недостающие бизнес-требования.
* **Критерий приемки**: на неполный запрос *«Посчитай выручку по городам»* агент задает структурированные вопросы по источникам, полям, формуле и правилам фильтрации.

### [Т13] Детерминированный чекер полноты параметров операций (`analyst/completeness/`)
* Декларативная матрица обязательных параметров для каждой операции MVP (`rules.py`):
  * для `join` обязательны: второй датасет, ключ соединения и тип join (обработка строк без пары);
  * для `with_columns` обязательна точная формула расчета;
  * для `aggregate` обязательны поля группировки и агрегатные функции.
* Программный чекер `CompletenessChecker`: принудительно блокирует статус готовности (`is_complete = False`), пока не заполнены обязательные параметры.
* Разделение требований: требования пользователя (`USER_EXPLICIT`) строго отделены от предложений аналитика (`AGENT_SUGGESTION`). Предложения аналитика требуют обязательного согласования пользователем.

### [Т14] Сборщик спецификации, валидация и защита от Out-of-Scope (`analyst/`)
* Класс `SpecificationBuilder` собирает согласованные требования в финальный объект `PipelineSpecification`.
* **Цикл самоисправления (Self-Correction Loop)**: при ошибках валидации Pydantic текст ошибки отправляется обратно в модель для автоматической корректировки (до 3 попыток).
* **Защита от выхода за рамки MVP (`out_of_scope.py`)**: отсекает неподдерживаемые запросы (машинное обучение, потоковые окна Kafka, неструктурированный NLP, графовые алгоритмы), возбуждая `OutOfScopeError`. Неподдерживаемые операции никогда не выдаются за реализованные.
* Формирование понятной человеку сводки спецификации для согласования перед проверкой.

### [Т15] Интерпретация результатов TLC, сценарий правок и версионирование (`analyst/formal_feedback.py`)
* Класс `FormalFeedbackExplainer` принимает структурированные результаты проверки `formal_check` (`PROPERTY_HOLDS`, `PROPERTY_VIOLATED`, `MODEL_INVALID`, `TIMEOUT`).
* **Исключение галлюцинаций**: шаги контрпримера берутся строго из реальной трассы TLC без выдуманных шагов.
* Формирует предложение по исправлению (`RevisionProposal`).
* Применяет изменение **только после явного согласия пользователя**, автоматически повышая версию спецификации по SemVer (`1.0.0` $\to$ `1.1.0`) и подготавливая ее к повторной верификации.

## 4. Воспроизводимая установка и быстрый старт (A11)

### Создание чистой среды и установка зависимостей
Требуется Python >= 3.12:
```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### Настройка переменных окружения
Скопируйте шаблон `.env.example` в `.env`:
```bash
cp .env.example .env
```
В файле `.env` задаются параметры:
```ini
GEMINI_API_KEY=ваш_ключ_google_ai_studio
GEMINI_MODEL=gemini-3.5-flash-lite
GEMINI_TEMPERATURE=0.2
GEMINI_TIMEOUT=30.0
GEMINI_MAX_RETRIES=3
USE_MOCK_CLIENT=false
RUN_LIVE_TESTS=false
```

### 1. Интерактивный диалог с аналитиком (CLI)
Запуск консольного диалога с поддержкой уточняющих вопросов, защиты от ложного согласования (A02) и отслеживания редакций (A05):
```bash
python analyst/cli.py
```
*(Для автономной работы без обращения к Gemini API используйте `USE_MOCK_CLIENT=true python analyst/cli.py`)*.

### 2. Запуск эталонного конвейера
Загрузка, Pydantic-валидация, построение топологического порядка DAG (9 шагов) и извлечение модели TLA+:
```bash
python pipeline_spec/examples/run_example.py
```

### 3. Запуск тестов

#### Оффлайн-прогон всех модульных и регрессионных тестов (71 оффлайн-тест):
```bash
pytest -v
```
Все 71 оффлайн-тест выполняются локально с детерминированными моками и `httpx.MockTransport`, не требуя внешнего сетевого подключения.

#### Запуск live-теста с реальным Google Gemini API:
```bash
RUN_LIVE_TESTS=true pytest -k test_live_gemini -v
```

## 5. Архитектурные границы и интеграционный контракт (A12, A13)

### Граница с модулем формальной проверки (`formal_check/`, Кирилл)
* Владелец директории `formal_check` — Кирилл (PR №4 / ветка `tla_tlc`).
* Модуль аналитика (`analyst/`) и контракт (`pipeline_spec/`) используют канонический входной интерфейс `formal_check.Input` через метод `PipelineFormalModel.to_formal_check_input()`.
* При переходе к проверяемой спецификации аналитик требует наличие валидной `formal_model` и проверяет ее семантическую корректность с помощью валидатора Кирилла (`validate_input`), не допуская скрытого пропуска проверок.

### Интеграционный контракт с Backend и генератором кода (Дмитрий)
1. **Версионирование**: `PipelineSpecification.version` ("1.0.0") является версией схемы/формата контракта. Редакция требований проекта передается backend'ом как отдельный целочисленный номер (редакция в БД).
2. **Согласование**: `AnalystResponse.is_complete == True` означает полноту собранных требований и согласие пользователя с предложениями диалога. Это не заменяет формальную верификацию TLC и не дает прямого разрешения на генерацию кода.
3. **Обратная связь TLC**: `FormalFeedbackExplainer` принимает машинный вердикт TLC, транслирует трассу контрпримера строго без придумывания шагов и формирует конкретное предложение guard для повторной проверки.
4. **Общий клиент**: `GeminiLLMClient` поддерживает внедрение готового экземпляра `genai.Client`, обеспечивая переиспользование сетевых ресурсов и общего rate limiter'а в `SharedGeminiClient`.
