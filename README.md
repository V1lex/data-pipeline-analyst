# Data Pipeline Analyst

Локальный MVP: диалог с DeepSeek через Polza AI → согласованная версия спецификации → формальная проверка TLA+/TLC → генерация и скачивание PySpark.

Ветки команды объединены с сохранением истории. Рабочая интеграция предназначена для `dev`; `main` остаётся стабильной базой.

```text
backend/
  src/
    api/                 FastAPI, HTTP-контракты
    agent/analyst/       диалог, полнота требований, согласование параметров
    agent/workflow.py    сохранение диалога и создание версий
    compiler/formal_check/  TLA+, TLC, нормализованный результат
    validator/           общий семантический валидатор
    pipeline_spec/       единый контракт PipelineSpecification
    pipeline_generator/ LLM-генерация и PostgreSQL-репозиторий
    db/                  SQLAlchemy-модели и запуск Alembic
    main.py
  alembic/               первая миграция + совместимая миграция MVP
  pyproject.toml
worker/src/runner.py     независимый процесс очереди FOR UPDATE SKIP LOCKED
frontend/               React + React Flow, Vite, nginx
infra/docker-compose.yml
scripts/download_tlc.py
```

Вложенные пакеты аналитика и формального движка сохранены для понятной связи с работой авторов. Все импорты имеют единую идентичность: `agent.analyst`, `compiler.formal_check`, `pipeline_spec`, `pipeline_generator`.

## Быстрый запуск в Docker

Нужны Docker Compose и Python для загрузки проверенного TLC. Настоящие ключи хранятся только в локальном `.env`.

```sh
cp -n .env.example .env
python3 scripts/download_tlc.py
docker compose --env-file .env -f infra/docker-compose.yml up --build
```

В `.env` укажите `POLZA_API_KEY`; `POLZA_MODEL` по умолчанию — `deepseek/deepseek-v4.1-flash-1017`. Compose использует `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` для внутреннего подключения; `DATABASE_URL` нужен при локальном запуске. Backend применяет Alembic, проходит healthcheck, затем запускается worker. Данные PostgreSQL остаются в именованном volume.

- Интерфейс: <http://localhost:3000>
- OpenAPI: <http://localhost:8000/docs>
- Проверка готовности БД и API: <http://localhost:8000/api/v1/health>

Остановка из корня проекта (сохранённая БД остаётся в Docker volume):

```sh
docker compose --env-file .env -f infra/docker-compose.yml down
```

Compose-файл лежит в `infra`, поэтому команда `docker compose down` без `-f` из корня его не найдёт. Локальные `uvicorn` и Vite, запущенные вне Docker, останавливаются через `Ctrl+C` в своих терминалах; Compose ими не управляет.

Для полного удаления контейнеров и тома базы (все сохранённые диалоги и файлы будут удалены):

```sh
docker compose --env-file .env -f infra/docker-compose.yml down --volumes --rmi local
```

## Разработка без Docker

Python 3.12+, PostgreSQL и Java 8+; Spark требуется только для отдельных демонстраций. Python-зависимости принадлежат `backend/pyproject.toml`, корень — uv workspace.

```sh
uv sync --extra dev
uv run python scripts/download_tlc.py
# DATABASE_URL и DATABASE_SCHEMA берутся из корневого .env
uv run python -m db.migrations
uv run uvicorn api.app:app --host 127.0.0.1 --port 8000
```

В отдельных терминалах:

```sh
uv run python -m worker.src.runner
npm ci --prefix frontend
npm run dev --prefix frontend
```

Vite открывается на <http://127.0.0.1:5173> и проксирует `/api` на порт 8000. При недоступности uv можно создать Python venv и установить `pip install -e './backend[dev]'`.

## Новый разговорный интерфейс

Основной экран — диалог. Первый отправленный запрос создаёт проект; последние диалоги доступны в боковой истории. «Схема» и «Файлы» открывают контекстные панели со спецификацией, согласованием, проверкой и артефактами выбранной версии. После перезагрузки открывается последний выбранный диалог. Меню `⋯` у чата позволяет переименовать его или удалить с подтверждением. Удаление убирает сообщения, все версии, результаты проверок и файлы этого чата; остальные диалоги сохраняются.

Потяните за левую границу правой панели, чтобы изменить её ширину. Размер общий для «Схемы», «Файлов» и результата проверки и запоминается в браузере; границу также можно выбрать клавиатурой и двигать стрелками.

Скрепка у поля сообщения прикрепляет файлы к запросу. Поддерживаются CSV, JSON (массив плоских объектов), JSONL (по плоскому объекту в строке) и Parquet с плоскими колонками, до 10 МиБ на файл и до 20 файлов на диалог по умолчанию; в одном сообщении — не более 20 файлов. Для текстовых файлов автоматически распознаются UTF-8 и Windows-1251; разделитель CSV определяется автоматически. Модель получает профили всех выбранных в диалоге файлов и до двух примеров строк на файл, а не полное содержимое. Профиль показывает выборку, поэтому типы и статистика не гарантируются для всего файла. По запросу о пропусках или явно заданным поддерживаемым правилам программа отдельно проверяет все строки до трёх выбранных файлов и передаёт модели фактические результаты. Примеры и ограничения распознавания описаны в [примере приёмки файла](examples/file-ingestion/README.md). Полный расчёт по файлам выполняет сгенерированный PySpark после подтверждения.

Кнопки действий расположены в правой панели: подготовка и согласование — в «Схеме», проверка и получение кода — в результате проверки. Кнопки под сообщениями открывают панели и файлы, не дублируя эти действия.

Профиль пока один: статичный `user`, без аккаунтов и входа. Авторизация остаётся отдельной задачей. Дизайн и подтверждение пользователя: `frontend/src/workspace-v4/landing.json`; принятый макет — `layout/full-page-v2.png`.

Для автоматического браузерного сценария без обращения к модели нужны отдельная тестовая PostgreSQL, Java/TLC и dev-зависимости. В трёх терминалах:

```sh
PYTHONPATH=. TEST_DATABASE_URL='postgresql://user:password@localhost/test_database' uv run python tests/browser_preview.py
DPA_API_TARGET=http://127.0.0.1:8001 npm run dev --prefix frontend -- --port 5174
FRONTEND_E2E_URL=http://127.0.0.1:5174 PLAYWRIGHT_CHANNEL=chrome npm run test:e2e --prefix frontend
```

QA API работает только на localhost, использует изолированную случайную схему с удалением при штатной остановке и подставленные ответы модели. PostgreSQL, очередь, API и Java/TLC настоящие. Это не проверка доступности Polza AI или качества сгенерированного моделью PySpark. `PLAYWRIGHT_CHANNEL=chrome` использует установленный Chrome; без него установите Chromium через `npx playwright install chromium` из frontend. Обычная сборка приложения никогда не включает этот QA API.

## Сценарий

1. Создайте проект, опишите задачу и ответьте на вопросы аналитика. Новые предложения требуют согласования; неполный или некорректный черновик не считается готовым.
2. Создайте спецификацию. Интерфейс показывает граф и полный JSON. Согласуйте конкретную версию.
3. Запустите TLC. Worker сохранит полный результат; интерфейс обновляется автоматически и показывает контрпример при нарушении.
4. После общего `PROPERTY_HOLDS` получите PySpark. Код и текст создаёт LLM; файл сохраняется за этой версией и доступен после перезапуска. Сетевой повтор использует тот же UUID, явная новая попытка — новый.
5. Изменения требований создают новую версию с отдельным согласованием и проверкой. Старые спецификации и выданные файлы не перезаписываются.

TLC проверяет конечную модель процесса, включая каждое `reachable`-свойство. Это не доказательство корректности сгенерированного Python. Отдельный исполнитель запускает сохранённый код только после явного подтверждения пользователя.

## Проверки

```sh
uv run pytest -q
uv run ruff check backend/src tests examples worker scripts
npm test --prefix frontend
npm run build --prefix frontend
docker compose --env-file .env.example -f infra/docker-compose.yml config --quiet
```

Для полной проверки используйте отдельную тестовую PostgreSQL с правом создания схем:

```sh
TEST_DATABASE_URL='postgresql://user:password@localhost/test_database' uv run pytest -q
```

Тесты создают случайные схемы и удаляют только их. Без `TEST_DATABASE_URL` проверки БД пропускаются. Реальные TLC-тесты требуют скачанный jar и Java. Spark-примеры запускаются отдельно с `RUN_SPARK_TESTS=1` и дополнением `backend[spark]`.

В интеграционных проверках используются настоящие PostgreSQL и Java/TLC. Отдельные Docker-тесты проверяют выполнение PySpark; браузерные тесты используют подставленные ответы модели. Для проверки Polza AI требуется действующий ключ.

## Границы текущего MVP

Сервис рассчитан на доверенную локальную разработку. Пользовательская авторизация и изоляция проектов ещё не реализованы. При аварийной остановке worker задание повторно забирается после истечения lease; прежняя попытка не может сохранить результат. Вычисления запускаются в отдельном ограниченном контейнере после подтверждения пользователя.

Единственный владелец схемы — Alembic. Миграция сохраняет данные первой версии Вани, но не выдумывает отсутствующие контексты и результаты старых проверок. Неверсионированная БД старого генератора отклоняется до DDL; её данные нужно переносить явно после резервного копирования. См. [интеграционный контракт](docs/integration.md), [ревью веток](docs/review-integration.md) и [подробности формального движка](docs/review-formal.md).


## Изолированное выполнение PySpark

Соберите подготовленный образ один раз и запустите отдельный локальный процесс исполнителя в другом терминале:

```sh
docker build -t dpa-spark-runner:local executor
uv run python scripts/run_executor.py
```

Нужен работающий Docker Desktop или Docker Engine; процесс получает настройки PostgreSQL из `.env` и не передаёт ключ Polza в вычислительный контейнер. Сам контейнер запускается без сети, без доступа к Docker socket, с read-only файловой системой и ограничениями CPU, памяти, времени, числа процессов и размера временного результата. В него передаются только выбранные для сохранённой версии входные файлы и её артефакт. Для Docker socket отдельного сервиса в Compose нет: очередь потребляет доверенный локальный процесс исполнителя.

Прикрепите источники к сообщению, согласуйте и проверьте версию, сгенерируйте код, откройте его в панели файлов, проверьте параметры и подтвердите запуск. Результат TLC и результат вычисления сохраняются отдельно; доступен архив и CSV, когда формат результата позволяет полный экспорт. Поддерживается PySpark 3.5.8 без дополнительных зависимостей. При изменении источников старые версии не изменяются, а текущий черновик нужно согласовать заново.

Для изолированной проверки на синтетических данных:

```sh
TEST_DATABASE_URL='postgresql://user:password@localhost/test_database' RUN_DOCKER_TESTS=1 TLC_WORKERS=1 uv run pytest tests/test_execution_real.py -q
```
