## 3. Что изменилось в схеме

### 3.1. Таблицы и поля

| Таблица | Исходное состояние → изменение |
| --- | --- |
| `projects` | Остались `id`, `name`, `description`, `created_at`; добавлены `analyst_state JSONB NOT NULL DEFAULT '{}'`, `state_revision integer NOT NULL DEFAULT 0`, `lease_token UUID`, `lease_until timestamptz` |
| `projects.description` | `NULL` заменяется на пустую строку; теперь `NOT NULL DEFAULT ''` |
| `specifications` | Добавлен nullable `context_json JSONB` со снимком требований, сообщений, окружения и полной pipeline specification |
| `verification_runs` | Добавлен `result_json JSONB` для полного нормализованного результата TLC, включая ошибки и diagnostics |
| `artifacts` | Добавлен допустимый вид `generation_manifest`; новый UNIQUE `(spec_id, kind, filename)` |
| `property_results` | Основные поля и связь с запуском сохранены; `status` переведён в text вместе с остальными указанными enum-колонками |
| `messages` | Основная структура сохранена; роль хранится как text с проверкой допустимых значений |

Для `projects/messages/specifications/artifacts.created_at` и `verification_runs.queued_at` добавлен серверный `clock_timestamp()`. Это важно для SQL-запросов через psycopg: Python `default=datetime.utcnow` в ORM не выполняется при прямом INSERT. UUID рабочий репозиторий передаёт явно; серверный генератор UUID этой миграцией не добавлялся.

### 3.2. Статусы: старые значения нельзя продолжать записывать

| Сущность | Было | Теперь |
| --- | --- | --- |
| Спецификация | `draft`, `confirmed` | `DRAFT`, `APPROVED` |
| Очередь проверки | `queued`, `running`, `completed`, `failed` | `QUEUED`, `RUNNING`, `FINISHED` |
| Вид артефакта | `pyspark`, `tla`, `cfg` | Те же значения плюс `generation_manifest` |
| Роль сообщения | `user`, `assistant`, `system` | Значения прежние |

Статус очереди и вердикт проверки разделены. И успешная проверка, и нарушение, и ошибка могут завершить попытку статусом `FINISHED`; итог находится в `verification_runs.result_json.status`.

В Python имена членов enum частично сохранены для совместимости: `SpecStatus.confirmed.value == 'APPROVED'`, `RunStatus.completed.value == 'FINISHED'`. Старого `RunStatus.failed` больше нет. Не сериализуй старое имя члена enum как значение БД.

Колонки `specifications.status`, `verification_runs.status`, `artifacts.kind`, `property_results.status`, `messages.role` преобразованы из PostgreSQL enum в **text**. На спецификации, очередь, вид артефакта и роль добавлены CHECK-ограничения; отдельный новый CHECK для `property_results.status` этой миграцией не добавлялся. Не следует считать все Python-enum автоматическими ограничениями PostgreSQL. Старые enum-типы после преобразования колонок могут оставаться в схеме.

### 3.3. Дополнительные ограничения и индекс

- Положительный номер версии: `version > 0`.
- `unique_project_version` из исходной схемы сохранён.
- `unique_run_property` из исходной схемы сохранён.
- Добавлен `unique_artifact_filename` для `(spec_id, kind, filename)`.
- Добавлен индекс `verification_spec_history` по `(spec_id, queued_at, id)`.
- Для запуска проверки `FINISHED` согласован с наличием `finished_at` и `result_json` через CHECK `finished_result_valid`.

Приложение при создании версии блокирует строку проекта и выделяет номер внутри короткой транзакции. При взятии очереди используется `FOR UPDATE SKIP LOCKED`; соединение не удерживается на время Java или LLM.

### 3.4. Неизменяемость обеспечивается в самой БД

Новая миграция создаёт три функции/триггера:

| Триггер | Что запрещает |
| --- | --- |
| `specification_immutable` | Изменение идентичности, версии, `spec_json`, `context_json`, времени создания; возврат согласованной версии в другой статус |
| `verification_immutable` | Перезапись завершённого результата, изменение идентичности запуска/версии/времени очереди, возврат `RUNNING` в `QUEUED` |
| `artifact_immutable` | UPDATE выданного файла; для `generation_manifest` разрешено изменение содержимого при сохранении идентичности |

Изменение требований создаёт новую версию, а не UPDATE старой. Эти триггеры относятся к UPDATE; каскадное удаление проекта и его дочерних записей ими не запрещено.

Если добавляешь восстановление очереди, простой `UPDATE ... RUNNING -> QUEUED` сейчас будет отклонён. Нужны согласованные изменения протокола lease и миграции триггера, а не обход проверки в приложении.

## 4. Как теперь запускаются миграции

Цепочка одна:

```text
12a5814e76d1 -> 20261101_mvp
```

Имя файла второй миграции длиннее её revision ID; в `alembic_version.version_num` ожидается `20261101_mvp`.

Основной вход из корня репозитория:

```sh
uv sync --locked --extra dev
uv run python -m db.migrations
```

Программный API:

```python
from db.migrations import upgrade

upgrade(dsn, schema="public", revision="head")
```

`PostgresRepository.migrate()` вызывает ту же цепочку. Отдельный прежний SQL-скрипт начальной схемы генератора удалён; второго независимого владельца таблиц больше нет. `Base.metadata.create_all()` не является заменой миграциям, поскольку не воспроизведёт протокол upgrade, ограничения и триггеры.

`migrations.py` проверяет имя схемы, передаёт соединение Alembic, использует `search_path` и хранит `alembic_version` в выбранной схеме. DSN `postgresql://` адаптируется для SQLAlchemy в `postgresql+psycopg://`.

В `env.py` подключение возможно через переданный connection или через `DATABASE_URL` из корневого `.env`. Сохранён `Base.metadata` для сравнения схемы. **Отдельный старый offline-путь `alembic --sql` не перенесён:** не считай его поддержанным без отдельной доработки и проверки.

Миграции и `alembic.ini` включены в wheel под пакетом `db`; запуск после установки не должен зависеть только от наличия checkout.

## 5. Что будет с существующей БД

### БД с исходной ревизией Вани

Если `alembic_version` указывает на `12a5814e76d1`, новая миграция добавит поля и ограничения и нормализует значения. Таблицы не удаляются и не пересоздаются. В частности:

- `description=NULL` превращается в `''`;
- `draft/confirmed` превращаются в `DRAFT/APPROVED`;
- `queued/running` превращаются в `QUEUED/RUNNING`;
- прежние `completed/failed` становятся `FINISHED`, но получают блокирующий `ENGINE_ERROR`: полного доверенного вердикта в прежних данных нет;
- старый `context_json` остаётся `NULL`: отсутствующий исторический снимок не выдумывается.

Таким образом, сохранение записей не означает, что каждая старая версия уже пригодна для генерации. Неполный контекст или отсутствующий положительный вердикт блокируют её.

Перед применением к ценной БД нужна резервная копия и проверка upgrade на её копии. В частности, новый UNIQUE может обнаружить уже существующие дубли артефактов; универсальная автоматическая чистка произвольных старых данных не реализована.

### БД с таблицами, но без истории Alembic

Если присутствуют pipeline-таблицы, а `alembic_version` отсутствует, `db.migrations.upgrade()` откажется до изменения схемы с сообщением `Unversioned existing pipeline schema`.

Автоматического `stamp head`, принятия произвольной generator-БД или угадывания структуры нет. Для таких данных требуется отдельный проверяемый перенос. Не отмечай схему актуальной только для обхода ошибки: это не создаёт отсутствующие столбцы и триггеры.

### Откат

В первой миграции улучшено удаление enum-типов при её `downgrade()`. Но **`downgrade()` новой `20261101_mvp` намеренно выбрасывает исключение**: безопасного обратного преобразования снимков и результатов пока нет.

Поэтому откат всей текущей БД через `alembic downgrade` не считается рабочим восстановлением. Для отката версии данных нужна заранее проверенная резервная копия либо отдельная разработанная обратная миграция. Исходный Git-коммит сам по себе БД не откатывает.

## 6. Где ORM, а где реальные запросы

SQLAlchemy-модели сохранены и используются Alembic как метаданные. Рабочий [PostgresRepository](../backend/src/pipeline_generator/storage.py) выполняет SQL через psycopg. Полного перевода API/worker/генератора на SQLAlchemy ORM не было.

При изменении поля нужно проверить минимум четыре места:

1. ORM-модель в `db/models.py`.
2. Новую Alembic-ревизию и фактические ограничения PostgreSQL.
3. SQL-запросы `storage.py`, `issuance.py` и потребляющий workflow.
4. HTTP/JSON-контракт и тесты сохранения/чтения.

Одной правки `mapped_column` недостаточно. Кроме того, нынешние CHECK, триггеры и дополнительный индекс не полностью описаны в ORM-метаданных: `autogenerate` — заготовка для ручного ревью, а не полное описание схемы.

## 7. Протоколы, которые важно сохранить

### Диалог

`begin_dialogue()` выдаёт token и снимок, устанавливая lease на пять минут. LLM работает без удержания DB-соединения. `commit_dialogue()` атомарно сохраняет снимок и сообщения, повышает `state_revision`, освобождает lease. При ошибке выполняется `abort_dialogue()`.

При создании спецификации token и срок lease повторно проверяются внутри транзакции вставки версии. Истёкший запрос не должен привязать старую спецификацию к новой переписке.

Этот lease защищает **диалог**, а не очередь TLC. Поля проекта нельзя считать готовым heartbeat/recovery для `verification_runs`.

### Проверка

Worker переводит запись `QUEUED -> RUNNING`, затем сохраняет `FINISHED` и весь `result_json`. `property_results` не заполняется выдуманным успехом для каждого свойства: сейчас отдельная строка сохраняется для реально сообщённого нарушенного свойства. Общий результат и diagnostics всегда нужно брать из запуска.

Генератор требует последнюю завершённую положительную проверку той же согласованной версии. Новая незавершённая попытка блокирует прежний успех.

### Генерация

`generation_manifest` хранится в таблице `artifacts`; `content` у него — JSON-текст. Его `id` соответствует `request_id`. Это отдельный протокол состояний `RUNNING/GENERATED/FAILED`, не статусы очереди TLC.

Резервирование выполняется до LLM-вызова. После ответа повторно проверяется fingerprint контекста; файл и результат manifest публикуются атомарно. Сетевой повтор с тем же UUID возвращает сохранённый результат. Явная новая попытка после сохранённого отказа использует новый UUID. Не удаляй manifest как «лишний файл»: это сломает защиту от повторной генерации.

### Переименование и удаление чата — добавлено 2 ноября

| HTTP | Поведение |
| --- | --- |
| `PATCH /api/v1/projects/{id}` с `{"name":"..."}` | Trim, 1–200 символов; обновляет только `projects.name`; ответ 200 с `id/name` |
| `DELETE /api/v1/projects/{id}` | Удаляет проект через существующие FK cascade; ответ 200 с `id` |
| Неизвестный UUID | 404 |
| Невалидное имя | 422 |

Переименование не меняет требования, сообщения, версии и `state_revision` диалога. Удаление каскадно убирает сообщения, спецификации, запуски, результаты свойств и артефакты. Если worker завершает уже удалённое задание, результат отбрасывается. Для этих функций миграция не добавлялась.

Пользовательская авторизация пока отсутствует, интерфейс содержит статичный `user`. Переименование/удаление не добавили проверку владельца: это отдельная задача перед общим размещением.

## 8. Запуск, Docker и диагностика

Из корня проекта, с локально заполненным `.env`:

```sh
python3 scripts/download_tlc.py
docker compose --env-file .env -f infra/docker-compose.yml up --build -d
docker compose --env-file .env -f infra/docker-compose.yml ps
```

Общий build context — корень репозитория. Backend устанавливается из `backend/`; worker получает тот же backend, Java и jar. Compose сначала ждёт PostgreSQL, запускает Alembic и API, ждёт healthcheck API, затем запускает worker/frontend.

Внутри Docker DSN собирается из `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`; `DATABASE_URL` из корневого `.env` нужен для локального запуска. После смены настроек существующей БД нужно отдельно сверить фактические роли/базу и сохранённый volume; изменение строки env не является миграцией данных.

```sh
# Остановка контейнеров; данные в volume остаются.
docker compose --env-file .env -f infra/docker-compose.yml down

# Логи только нужных сервисов.
docker compose --env-file .env -f infra/docker-compose.yml logs --tail=100 backend worker
```

Без `-f` из корня Compose не найдёт файл в `infra`. Обычный `down` не удаляет volume; вариант с `-v` меняет это поведение и не нужен для обычного перезапуска. `uvicorn` и Vite, запущенные вне Docker, Compose не останавливает; их нужно завершать отдельно через Ctrl+C в соответствующих терминалах. Это также устраняет конфликт занятого порта 8000.

Локальный backend:

```sh
uv sync --locked --extra dev
uv run python -m db.migrations
uv run uvicorn api.app:app --host 127.0.0.1 --port 8000
```

Адреса: UI `http://localhost:3000`, OpenAPI `http://localhost:8000/docs`, readiness `http://localhost:8000/api/v1/health`. Успешный healthcheck подтверждает доступность таблиц, но не проверяет Gemini или работоспособность всей цепочки.

## 9. Как добавлять следующую миграцию

Для новой работы можно создать ветку от общей базы:

```sh
git fetch origin
git switch -c vanya/database-next origin/dev
```

Если продолжаешь исходную ветку, сначала включи `origin/dev` обычным merge. Не возвращай поверх общей схемы старые enum-статусы и не создавай второй init SQL. Переписывать опубликованную историю не требуется.

Следующая ревизия должна ссылаться на текущую head `20261101_mvp`. Не переписывай применённую историю для новой задачи. При изменении данных/constraint/triggers опиши upgrade, поведение на существующих записях и реальную стратегию восстановления.

Команда для заготовки после настройки отдельной dev-БД:

```sh
uv run alembic -c backend/alembic.ini revision --autogenerate -m "describe_change"
```

Просмотри полученный файл вручную. Не применяй предложенное autogenerate удаление ограничения или индекса только потому, что его нет в ORM-модели. На копии данных проверь и новую пустую БД, и обновление с предыдущей head.

## 10. Проверки и оставшиеся задачи

Целевые тесты, с отдельной тестовой БД и правом создания схем:

```sh
TEST_DATABASE_URL='postgresql://user:password@localhost/test_database' uv run pytest -q tests/test_migrations.py tests/test_storage.py tests/test_api.py tests/test_worker.py
uv run ruff check backend/src/db backend/src/pipeline_generator tests worker
docker compose --env-file .env.example -f infra/docker-compose.yml config --quiet
```

Тесты используют случайные схемы и удаляют их после завершения. Без `TEST_DATABASE_URL` DB-тесты пропускаются. Проверка `compose config` не является проверкой реального запуска контейнеров.

Последний общий прогон перед этим документом: **220 backend passed, 7 skipped; 16 frontend unit passed; 6 browser scenarios passed**. Настоящие PostgreSQL и Java/TLC проверены; пропущены 6 отдельных Spark-демонстраций и live Gemini test. Документ фиксирует уже полученные результаты, а не новый прогон тестов.

В текущем Docker-запуске подтверждены создание БД, доступность API и операции проектов. Живой Gemini возвращает `400 FAILED_PRECONDITION` по региону; backend показывает общее `502 LLM_REQUEST_FAILED`. Это не сбой PostgreSQL. Полная цепочка с ответом Gemini и исполнением именно сгенерированного PySpark ещё не подтверждена.

Приоритеты дальнейшей работы:

1. **Worker recovery:** started/lease/heartbeat, безопасное повторное получение зависшего задания, защита от завершения устаревшим worker. Учесть нынешний immutable trigger.
2. **Согласованность metadata/DDL:** явно описать и проверить ограничения и индексы, чтобы autogenerate не предлагал неожиданных изменений.
3. **CI и контейнерный сценарий:** реальные PostgreSQL/Java, Alembic upgrade с исходной ревизии, сборка и запуск четырёх сервисов.
4. **Авторизация:** владелец проекта и проверка прав во всех маршрутах, включая файлы и удаление.
5. **Перенос старой неверсионированной БД**, если нужен: отдельный план и проверка данных вместо автоматического stamp.
6. **Восстановление и эксплуатация:** проверяемый backup/restore, лимиты очереди и наблюдаемость; отдельно решить необходимость offline Alembic.
