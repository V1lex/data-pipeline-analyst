## 2. Где теперь лежит код

Старый каталог `formal_check/` перенесён в [backend/src/compiler/formal_check](../backend/src/compiler/formal_check/). Вложенная структура сохранена, чтобы оставалась понятна связь с исходной реализацией.


Импорты теперь начинаются с `compiler.formal_check`, например:

```python
from compiler.formal_check.src.models.input import Input
from compiler.formal_check.src.services.checker import check_model
```

Глобальные импорты `from src...` больше не используются. Запуск и зависимости принадлежат общему backend/корневому uv workspace; отдельный `formal_check/pyproject.toml` удалён.

## 4. Какие изменения поведения нужно учитывать

### 4.1. Прогресс больше не считается успешной проверкой

Раньше парсер мог вернуть `PROPERTY_HOLDS`, найдя сообщение `Progress(...)`. Оно показывает промежуточное состояние обхода и не подтверждает успех.

Теперь для положительного результата нужны сообщение об успешном завершении, финальная статистика, нулевая очередь оставшихся состояний и глубина завершённого обхода. Пустой, оборванный или ошибочный вывод не становится успехом. Нарушение инварианта должно сопровождаться читаемым контрпримером.

### 4.2. Reachable проверяется отдельно

Раньше генерация reachable-конфигураций оставалась TODO. Теперь для каждого свойства `reachable` создаётся отдельный запуск с инвариантом отрицания целевого предиката.

- Нарушение именно этого отрицательного инварианта даёт свидетельство достижимости.
- Полностью завершённый обход без такого нарушения означает недостижимость и общий `PROPERTY_VIOLATED`.
- Ошибка другого свойства или `TypeOK` не считается свидетельством достижимости.
- Общий успех возвращается после safety и всех запрошенных reachable-проверок.

Это внутренняя техника проверки. Нельзя напрямую принять любой `PROPERTY_VIOLATED` отдельного TLC-запуска за отрицательный итог всего запроса: для reachable смысл результата преобразует `checker.py`.

### 4.3. Семантика остальных свойств

| Тип | Текущее значение |
| --- | --- |
| `invariant` | Выражение должно выполняться во всех достижимых состояниях |
| `forbidden_state` | Проверяется отрицание заданного запрещённого состояния |
| `deadlock_free` | Должен существовать разрешённый переход либо выполняться переданный предикат допустимого конечного состояния |
| `reachable` | Должно существовать достижимое состояние с заданным выражением |

Безусловное сгенерированное свойство `IsDAG` удалено. Циклы в формальной модели допустимы, если их не запрещает объявленное свойство. Проверка DAG графа конвейера относится к другому, более высокому уровню `pipeline_spec`; эти два требования нельзя смешивать.

### 4.4. Валидация стала строже

Исходный Pydantic-контракт сохранён, но валидатор теперь проверяет то, что ранее могло пройти через заглушку `_validate_expression()`:

- начальное значение каждой переменной и отсутствие неизвестных переменных;
- типы, enum-домены, границы целых чисел;
- ссылки в guard, свойствах и правых частях присваиваний;
- Boolean-операнды логических операций и integer-операнды арифметики/сравнений;
- существование и тип цели присваивания, отсутствие повторного присваивания в одном переходе;
- имена TLA+, зарезервированные слова и конфликты имён между переменными, переходами и свойствами.

Дополнительно компилятор создаёт `TypeOK`. Если переход динамически выводит переменную за объявленный домен, общий результат — `MODEL_INVALID` с трассой. Формально валидная структура JSON сама по себе не гарантирует допустимость модели.

### 4.5. Изоляция запусков и строки

`check_model()` создаёт отдельную временную папку. `run_tlc()` также запускает Java в собственной рабочей директории. Это предотвращает смешение моделей и служебных файлов параллельных заданий.

Старые глобальные пути в `config.py` сохранены для низкоуровневых функций, но непригодны для конкурентной обработки без явного `output_dir` и явных путей runner.

Строковые литералы проходят через `strings.py`: Unicode и строки со служебным префиксом кодируются в однозначные ASCII-токены, а в нормализованном контрпримере восстанавливаются. Сырой `diagnostics.stdout` может содержать токены. При добавлении новых строковых операций нужно отдельно проверить, сохраняет ли такое кодирование их семантику; сейчас оно рассчитано на равенство и принадлежность множеству.

## 5. Основной API для остальных частей проекта

Рабочий вход — [checker.py](../backend/src/compiler/formal_check/src/services/checker.py):

```python
def check_model(data: dict, *, jar_path=None, timeout: float = 30) -> dict:
    ...
```

`data` — формальный `Input`, не весь `PipelineSpecification`. Полный конвейер хранится отдельно и содержит формальную часть. `timeout` — общий бюджет всех запусков TLC в одном вызове, а не новый полный бюджет на каждое свойство.

Низкоуровневые функции сохранены:

| Функция | Результат и особенности |
| --- | --- |
| `validate_input(data)` | `Input` либо `ModelInvalid` |
| `compile_input(input_data, *, output_dir=None)` | Создаёт `.tla`/`.cfg`, возвращает `None` |
| `run_tlc(timeout=5.0, *, model_path=None, config_path=None, jar_path=None)` | `RunnerOutput` с stdout/stderr/exit code/техническим статусом |
| `parse_tlc_output(stdout, variables)` | **JSON-строка**, не Python dict |

Технический `Status.SUCCESS` runner означает, что вывод можно интерпретировать. Он не означает `PROPERTY_HOLDS`: TLC может штатно завершиться ненулевым кодом 11/12 при нарушении инварианта. Общий вердикт определяет checker.

### Формат результата

| `status` | Значение для приложения |
| --- | --- |
| `PROPERTY_HOLDS` | Все необходимые проверки завершены успешно; есть `engine=TLC` и `statistics` |
| `PROPERTY_VIOLATED` | Нарушено объявленное свойство либо не достигнута reachable-цель; указан `property_id` |
| `MODEL_INVALID` | Структурная/семантическая ошибка или выход за домен; есть `errors` |
| `TIMEOUT` | Проверка не уложилась во время; положительный вердикт не установлен |
| `ENGINE_ERROR` | Некорректный вывод, ошибка движка или внутреннего выполнения проверки |
| `INFRASTRUCTURE_ERROR` | Нет jar/Java, JVM аварийно завершена либо другая ошибка окружения |

`diagnostics` содержит сведения по отдельным запускам: `configuration`, `exit_code`, `stdout`, `stderr`. При успешной агрегации также есть `checked_properties`; статистика относится к safety-запуску, это не сумма статистик всех reachable-запусков.

При недостижимой цели контрпример может быть пустым: отсутствует путь-свидетель, а не потеряна трасса нарушения. `STATE_LIMIT_REACHED` существует в общих контрактах проекта, но отдельной ветки выдачи такого результата текущий `check_model()` не реализует.

## 6. Как модуль связан с БД, API и генератором

```text
Согласованная версия -> POST /specifications/{id}/verify
  -> verification_runs: QUEUED
  -> worker забирает запись через FOR UPDATE SKIP LOCKED
  -> RUNNING, транзакция и соединение освобождены
  -> check_model(spec_json)
  -> FINISHED + полный result_json
  -> генератор проверяет последний запуск этой же версии
```

Статус очереди `FINISHED` означает завершение попытки, включая ошибку или нарушение. Фактический вердикт находится в `result_json.status`.

Генерацию разрешает только согласованная версия с последним завершённым `PROPERTY_HOLDS`, `engine=TLC` и статистикой. Новый `QUEUED`/`RUNNING` блокирует использование прежнего успеха. Публичного HTTP-метода записи произвольного положительного вердикта нет.

С 2 ноября пользователь может удалить чат вместе с версиями и заданиями. Если запись исчезла до или во время проверки, worker отбрасывает результат отсутствующего задания. Это не механизм автоматического восстановления упавшего worker.

`.tla` и `.cfg` создаются во временных папках и автоматически удаляются. Допустимые виды артефактов БД включают `tla`/`cfg`, но текущий worker не публикует их автоматически как сохранённые файлы.

## 7. Запуск и проверка

Все команды ниже выполняются **из корня репозитория** после настройки `.env`.

```sh
uv sync --locked --extra dev
uv run python scripts/download_tlc.py
java -version
```

Jar хранится в `worker/tla2tools.jar`, в Git не добавляется. Скрипт закрепляет release `v1.7.4` и проверяет SHA-256 перед заменой файла. При обновлении jar нужно менять версию и checksum вместе и проверять реальные форматы вывода. Для установленного wheel вне checkout лучше явно передать `TLC_JAR_PATH` или `jar_path`.

Пример программного запуска без Gemini и без БД:

```sh
uv run python - <<'PY'
from compiler.formal_check.src.services.checker import check_model

model = {
    "variables": [{"name": "x", "type": "integer", "min": 0, "max": 1}],
    "initial": {"x": 0},
    "transitions": [{"name": "Advance", "effects": [{"set": ["x", 1]}]}],
    "properties": [{"id": "P", "type": "reachable", "expression": {"eq": [{"var": "x"}, 1]}}],
}
result = check_model(model, timeout=30)
print(result)
assert result["status"] == "PROPERTY_HOLDS"
PY
```

Для существующего JSON-файла формального `Input`:

```sh
uv run python -m compiler.formal_check.src.main /path/to/model.json --timeout 30
```

Для очереди нужны PostgreSQL и применённые миграции:

```sh
uv run python -m db.migrations
uv run python -m worker.src.runner
```

Параметры: `DATABASE_URL`, `DATABASE_SCHEMA`, `TLC_JAR_PATH`, `JAVA_BIN`, `TLC_TIMEOUT`, `WORKER_POLL_INTERVAL`. У прямого вызова checker время задаётся аргументом `timeout`; `TLC_TIMEOUT` читает процесс worker.

Целевые проверки:

```sh
uv run pytest -q backend/src/compiler/formal_check/tests
TEST_DATABASE_URL='postgresql://user:password@localhost/test_database' uv run pytest -q tests/test_worker.py tests/test_api.py
uv run ruff check backend/src/compiler/formal_check worker tests/test_worker.py
```

БД для тестов должна быть отдельной и разрешать создание схем. Тесты создают случайные схемы и удаляют их. Без `TEST_DATABASE_URL` проверки БД пропускаются; часть реальных TLC-тестов пропускается без jar. Один зелёный прогон с такими пропусками не равен полной проверке.

## 8. Как дальше работать с кодом

Для новой задачи можно создать ветку от общей актуальной базы:

```sh
git fetch origin
git switch -c kirill/tlc-next origin/dev
```

Если продолжаешь старую `tla_tlc`, сначала включи в неё актуальную `origin/dev` обычным merge и проверь конфликты. Не копируй обратно старый каталог `formal_check/`: рабочие изменения теперь делаются по новому пути. Переписывать опубликованную историю или делать force push для этого не требуется.

При изменении формата результата проверь вместе `models/output.py`, parser, checker, repository, генерационный gate и отображение результата. При изменении DSL проверь также преобразование из `pipeline_spec`. Перед PR в `dev` сохрани регрессии на ошибочные и неполные выводы, reachable, domain overflow и конкурентные запуски.

## 9. Что остаётся сделать и что уже подтверждено

Последний общий прогон перед этим документом: **220 backend passed, 7 skipped; 16 frontend unit passed; 6 browser scenarios passed**. Реальные PostgreSQL и Java/TLC использовались; ответы модели в browser QA были подставлены. Пропущены 6 явно включаемых Spark-демонстраций и один live Gemini test.

Образы Docker собраны и API/БД запускались, но полный сценарий с живой моделью не подтверждён: Google возвращает `400 FAILED_PRECONDITION / User location is not supported for the API use`. Это отдельная проблема доступа к Gemini, не отрицательный вердикт TLC.

Дальнейшие задачи:

1. Lease/heartbeat/reclaim для очереди после жёсткого завершения worker; устаревший процесс не должен завершать повторно выданное задание.
2. Явные лимиты и наблюдаемость больших пространств состояний. Сейчас runner ограничивает Java-память `-Xmx512m` и время; это не полноценное управление ресурсами.
3. CI с реальными Java/TLC и PostgreSQL, включая конкурентность и сценарии остановки worker.
4. При необходимости — сохранение исходных `.tla`/`.cfg` как версионных артефактов.
5. Полная демонстрация через доступный Gemini и отдельная проверка исполнения полученного PySpark.

Проверка конечной TLA+-модели не доказывает корректность сгенерированного Python или реальной обработки данных. При планировании следующих задач эти проверки нужно учитывать отдельно.
