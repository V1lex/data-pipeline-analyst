# Проверки реализации — 30 октября 2026

## Подтверждено

На Python 3.12.12 с PostgreSQL 18.1 выполнен полный текущий набор: **65 passed**. PostgreSQL был отдельным временным кластером с локальным Unix-сокетом, без доступа к пользовательским БД. Каждый тест создавал свою схему.

```sh
TEST_DATABASE_URL='...выделенная тестовая PostgreSQL...' uv run pytest -q
uv run ruff check src tests examples
```

Результат Ruff — `All checks passed!`. Фактические проверки выполнялись из папки проекта отдельным временным Python-окружением; команды выше — эквивалент для воспроизведения через `uv`.

Проверена сборка wheel командой `uv build --wheel`; пакет успешно собран, `generation_prompt.md` и `migrations/001_initial.sql` доступны через `importlib.resources` из wheel, а не только из исходников.

Проверено поведение:

- Сборка запроса из согласованного снимка и конкретной версии, без подмешивания поздних сообщений.
- Все запрещающие статусы, неподтверждённый контекст, отсутствие статистики, новая непроверенная версия и новый незавершённый запуск.
- Успех/уточнения, пустой и обрезанный ответ, неверный JSON/типы/имя файла, ошибки авторизации/сети, ограниченные повторы.
- Чтение `.env` с приоритетом окружения, безопасная диагностика доступа и отсутствие ключа в отслеживаемых файлах.
- Хранение проектов, сообщений, неизменяемых версий, полных ответов и только явно известных результатов свойств.
- Чтение сохранённого снимка отдельным свежим Python-процессом.
- Идемпотентная и конкурентная выдача, отдельные файлы при регенерации, отсутствие открытой транзакции во время LLM.
- Повторная проверка допуска перед сохранением и откат при ошибке записи файла в БД.
- Истёкший незавершённый запрос требует явного нового ключа, не вызывает скрытый повтор LLM.

## Независимое ревью

Ревью основных модулей подтвердило корректное использование блокировки версии и коротких транзакций. Найдены два случая: Unicode-суррогаты и чрезмерная вложенность JSON могли оставить попытку RUNNING. Четыре регрессионных сценария сначала воспроизвели ошибки, затем прошли после исправления границы разбора ответа. Некорректный ответ теперь получает `LLM_INVALID_RESPONSE` и сохранённое состояние FAILED.

## Gemini

Выполнен настоящий минимальный запрос к официальному `generateContent` без данных проекта. Ответ: HTTP 400, `FAILED_PRECONDITION`, `User location is not supported for the API use.` Успешной генерации кода пока не было.

Пользователь указал считать тестовый ключ рабочим и отложить исправление локации. По его прямому указанию ключ сохранён только в локальном `.env` с правами `0600`; `.env` игнорируется Git. Значение не входит в документацию, тесты, журнал или коммит. Модель — конфигурируемая `gemini-3.1-flash-lite`; автоматического перехода на платный тариф или другую модель нет.

Реальный запрос со структурированным выходом остаётся непроверенным из-за локации. Контракт HTTP и обработка ответов проверены на транспортных тестах, что не заменяет live-успех.

## Spark и полная интеграция

Подготовлены два явно помеченных ручных образца и шесть отдельных Spark-проверок. Их результат фиксируется отдельно от 65 основных тестов. Настоящий результат Gemini через Spark ещё не выполнялся, поэтому полный критерий T26 не закрыт.

Шесть Spark-проверок фактически выполнены на PySpark 3.5.8, Python 3.12.12 и Java 8u451: **6 passed in 5.93s**. Получены Москва = 300 и Казань = 150, north = (15.0, 2), south = (-5.0, 1). Ошибки пустых полей/дубликатов остановили обработку до записи; существующий выходной каталог сохранён.

```sh
RUN_SPARK_TESTS=1 uv run pytest -m spark -q
# Полный совместный прогон:
RUN_SPARK_TESTS=1 TEST_DATABASE_URL='...тестовая PostgreSQL...' uv run pytest -q
```

В `.python-version` зафиксирован Python 3.12 для воспроизведения; `uv python find` подтвердил выбор установленного 3.12. PySpark был установлен из официального архива PyPI после проверки SHA-256, не из сторонней сборки.

Backend/UI Вани и парсер результатов Кирилла в эту ветку не реализовывались. Предоставлены интерфейс и пример подключения в `integration.md`; полного пользовательского маршрута через реальные модули команды пока нет.

## Проверка контрактов актуальной команды

Подключены read-only копии исходников веток Андрея `7a08e06` и Кирилла `7065373`. Тесты `test_team_integration.py` импортируют настоящие модели команды; без этих пакетов связанные проверки пропускаются, не заменяются копиями классов. Для воспроизведения укажите корень checkout аналитика и его formal_check в PYTHONPATH. SDK-тесты используют дополнение `team`:

```sh
uv sync --extra dev --extra team --extra spark
PYTHONPATH='/path/to/analyst-checkout:/path/to/analyst-checkout/formal_check' \
  RUN_SPARK_TESTS=1 TEST_DATABASE_URL='...тестовая PostgreSQL...' uv run pytest -q
```

Проверены: роль model→assistant, целая PipelineSpecification и штатное преобразование формальной модели, сохранение значимых null, отдельные версии формата и редакции, блокировка без подтверждения, канонический объект/JSON checker, прежний fingerprint. Настоящий Google SDK с локальным MockTransport проверяет сериализацию схемы и безопасную обработку повреждённых HTTP200-ответов; ошибочные запросы получают manifest FAILED. Это не live-запрос к Google и не настоящий запуск TLC.

Отдельный существующий набор ветки Андрея: **38 passed, 1 skipped**; пропущен только live-тест без ключа в окружении этой копии. Для Кирилла создан draft PR №4 без изменения его кода; 15 тестов входной модели прошли. Сферу по последнему указанию пользователя не обновляем — карточки он передвинет самостоятельно.
