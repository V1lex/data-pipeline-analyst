# Контракт генератора PySpark, v1

Дата: 2026-10-30. Область: T22–T26 Дмитрия. Основание — карточки MNTL-28–32 и обновлённая постановка с LLM-генерацией. Это интерфейс реализации данной ветки для подключения Ваней, не утверждение о готовой интеграции всей команды.

## Граница доверия

Backend после своей авторизации вызывает `GenerationService.generate(spec_id: UUID, request_id: UUID)`. Он не передаёт клиентский `PROPERTY_HOLDS`: сервис читает подтверждённую версию и последний запуск из PostgreSQL. Метод записи результата проверки предназначен только для доверенного worker, не для пользовательского HTTP-запроса.

Доступ разрешён, только если версия `APPROVED`, у последнего запуска `FINISHED`, а сохранённый общий ответ содержит `status=PROPERTY_HOLDS`, `engine=TLC` и статистику. Технический `success` runner не принимается. Все другие статусы, незавершённый запуск и отсутствие запуска блокируют генерацию. Новая версия требует собственного согласования и проверки. Пустой список свойств не допускает выдачу «проверенного» процесса.

Формальный DSL и его проверка остаются у Кирилла. Модель хранится без добавления генераторных операторов. Генератор не интерпретирует TLC stdout, не чинит модель и не запускает Python.

## Контекст версии

При создании версии сохраняются:

- `spec_json` — исходный формальный JSON;
- `context_json.approved_requirements` — согласованная постановка с данными и формулами;
- `context_json.messages` — снимок выбранных сообщений этого проекта с их UUID, ролями и содержимым;
- `context_json.target_environment` — версия PySpark и дополнительные зависимости.
- `context_json.pipeline_specification` — необязательный полный снимок валидированного `PipelineSpecification` аналитика. Сохраняет значимые `null`, схемы, формулы и операции; формальная часть преобразуется штатным методом команды в `spec_json`.

Backend передаёт список UUID сообщений, которые соответствуют этой постановке; произвольная последняя переписка не подмешивается. Более поздние сообщения не меняют снимок. Модель, снимок и номер версии неизменяемы на уровне БД. Новые требования создают новую версию.

Сервис формирует `VerifiedContext`: `spec_id`, `spec_version`, `verification_run_id`, `approved_requirements`, `messages`, `behavioral_model`, `verification_result`, `target_environment`, необязательный `pipeline_specification`. SHA-256 канонического JSON связывает попытку и файл с конкретным контекстом. При отсутствии новой опции хеш старого контекста сохраняется. Хеш — контроль соответствия, не электронная подпись и не замена доверенному worker.

## LLM-интерфейс

`LlmClient.complete(system: str, user: str, response_schema: dict) -> Completion`.
`Completion` содержит `text`, `finish_reason`, `provider`, `model`. Успех требует явного `STOP`; `MAX_TOKENS` — обрезанный ответ, остальные причины — блокировка/незавершённость.

Ответ модели — JSON:

```json
{
  "status": "GENERATED",
  "answer": "Подготовлен скрипт расчёта выручки по городам. Передайте пути заказов, цен и нового Parquet-назначения.",
  "filename": "revenue_by_city.py",
  "content": "from pyspark.sql import SparkSession\n...",
  "requirements": ["pyspark==3.5.8"],
  "notes": [],
  "questions": []
}
```

`answer` — непустой обычный текст модели для пользователя; `content` — отдельно полный Python-код той же модели. Обвязка передаёт контекст LLM, проверяет оболочку ответа и сохраняет результат; вычислительный код или пользовательское объяснение сама не сочиняет. JSON используется внутри API: UI показывает текст и отдельно код/файл.

Если требований не хватает: `status=NEEDS_CLARIFICATION`, `answer` объясняет, что нужно уточнить, пустые `filename/content`, непустой `questions`. Модель не придумывает источники, столбцы и бизнес-правила. Выход не ограничен каталогом вычислительных операций; DataFrame API предпочтителен, `spark.sql` не запрещён.

JSON проверяется строго: неизвестные поля, неправильные типы, небезопасное имя файла, пустой код или выход больше 2 MiB отклоняются. Это проверка оболочки, не доказательство корректности Python.

Успешный ответ сервиса содержит `status=GENERATED`, `answer`, `artifact_id`, `spec_id`, `spec_version`, `verification_run_id`, `request_id`, `filename`, `content`, `requirements`, `notes`, `provider`, `model`, `context_sha256`, `code_validation=not_performed`. Сервис всегда добавляет пояснение: проверена модель процесса, корректность сгенерированного кода автоматически не проверялась.

Текст ответа хранится в result существующего generation_manifest; схема PostgreSQL не меняется. Ранее сохранённые результаты без answer остаются читаемыми с пустым answer: новый ответ модели для них не придумывается и повторная генерация молча не запускается. В ответах новых LLM-вызовов поле обязательно.

## Хранение

Шесть базовых таблиц из схемы сохранены. Явные дополнения в миграции этой ветки:

1. `specifications.context_json JSONB NOT NULL` — снимок требований и сообщений.
2. `verification_runs.result_json JSONB` — полный общий нормализованный результат, в том числе ошибки без `property_id`.

Эти поля нужны для корректной привязки и представлены backend как конкретное предложение интеграции. Чужих миграций пока нет; перед объединением другой схемы требуется сопоставление, не повторное создание таблиц. Миграция запускается явно в пустой согласованной схеме PostgreSQL, а не при каждом импорте.

`property_results` получает только явно известные результаты: при нарушении — указанное свойство; общий положительный результат хранится в запуске без выдуманных строк для остальных свойств. Все диагностики/контрпримеры общего ответа сохраняются в `result_json` без переименования исходных статусов. `ENGINE_ERROR` и `INFRASTRUCTURE_ERROR` допустимы и оба запрещают генерацию.

Новые значения локальных CHECK-ограничений определены в SQL, потому что утверждённых enum-миграций нет: спецификация `DRAFT/APPROVED`, запуск `QUEUED/RUNNING/FINISHED`, роль сообщения `user/assistant/system`, артефакт `tla/cfg/pyspark/generation_manifest`. Они не подменяют нормализованные статусы model checker.

## Повторы и частичные ошибки

`request_id` — ключ идемпотентности, который backend сохраняет на время одного пользовательского запроса. Повтор того же ключа возвращает тот же файл; ключ другой версии или другого контекста отклоняется. Новый ключ означает намеренную повторную генерацию и сохраняет отдельный файл с UUID в имени.

Короткая транзакция резервирует `generation_manifest` в `artifacts`; соединение закрывается до вызова LLM. Во время LLM нет открытой транзакции или блокировки БД. Одновременный повтор возвращает `GENERATION_IN_PROGRESS`. Успешный PySpark-файл и завершённый manifest записываются атомарно. Ошибка не меняет результаты TLC.

После аварийного завершения процесса manifest может остаться RUNNING. Сервис не перезапускает неизвестный внешний вызов автоматически: по истечении срока выдаёт `GENERATION_EXPIRED`, а backend предлагает явный повтор с новым ключом. Этот выбор ограничивает скрытое дублирование; фонового воркера восстановления в этом модуле нет.

## Ошибки

`PipelineError` содержит безопасные `code`, `message`, `retryable`, `details`. Основные коды: `NOT_FOUND`, `VERIFICATION_REQUIRED`, `CONTEXT_REQUIRED`, `NEEDS_CLARIFICATION`, `CONFIGURATION_ERROR`, `LLM_AUTH_ERROR`, `LLM_ACCESS_ERROR`, `LLM_TRANSIENT_ERROR`, `LLM_TIMEOUT`, `LLM_BLOCKED`, `LLM_TRUNCATED`, `LLM_INVALID_RESPONSE`, `EMPTY_CODE`, `REQUEST_CONFLICT`, `GENERATION_IN_PROGRESS`, `GENERATION_EXPIRED`, `STORAGE_ERROR`.

Временные сетевые/429/5xx ошибки можно повторить ограниченно; конфигурация, авторизация, неверный формат и нехватка требований не повторяются. Ключи, DSN и полный HTTP-ответ не включаются в диагностику.

## Выдача backend

`repository.get_artifact(spec_id, artifact_id)` возвращает только артефакт нужной версии. Backend проверяет доступ пользователя к проекту, задаёт `Content-Type: text/x-python; charset=utf-8` и безопасный `Content-Disposition: attachment`. Готовый пример интеграционного вызова расположен в `docs/integration.md`. HTTP-маршруты и UI не реализуются за Ваню.

## Внешние проверки

Fake-клиент доказывает поведение модуля, но не доступ к Gemini. Ручной пример не является результатом модели. Только отдельно выполненный live-запрос и запуск именно полученного файла закрывают соответствующие части T24/T26. Недоступные внешние проверки остаются BLOCKED.
