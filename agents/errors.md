## ERR-004 — Некорректный Unicode/глубокий JSON оставляли запрос RUNNING

- Статус: RESOLVED
- Дата: 2026-10-30
- Область: generator / integration
- Симптом: UnicodeEncodeError при сохранении одинокого суррогата или RecursionError при разборе JSON обходили PipelineError; повтор видел незавершённую попытку.
- Как воспроизвести: fake STOP-ответ с `chr(0xD800)` в исходном тексте/content/notes либо JSON из 20 000 вложенных массивов.
- Ожидание: безопасный `LLM_INVALID_RESPONSE`, попытка FAILED, без готового файла и без повторного обращения по тому же ключу.
- Факт до исправления: четыре регрессионных сценария завершались необработанными исключениями.
- Причина: разбор не проверял UTF-8 всех строк после JSON-декодирования и не перехватывал RecursionError.
- Связанные попытки: TRY-005.
- Исправление: проверка UTF-8 исходного и разобранного ответа; нормализация ошибки вложенности в `generator.py`.
- Проверка: четыре сценария проходят, повтор возвращает сохранённую ошибку; весь основной набор — 65 passed с PostgreSQL.
- Ограничения: проверка оболочки не доказывает исполнимость или бизнес-корректность Python.

### Обновление ERR-002 — новая ветка 7065373

- Статус: IN_PROGRESS у формального модуля.
- Ветка обновлена и прочитана: парсер теперь реализован как `parse_tlc_output(stdout, variables) -> str`. Первоначальная запись о пустом файле относится к предыдущему коммиту 77eba11.
- Схема нормализованного успеха совместима, но текущий код выводит PROPERTY_HOLDS по progress-статистике без явной проверки завершения. Для reachable в compiler/runner всё ещё есть TODO.
- Наш модуль не исправляет и не подменяет парсер Кирилла. Интеграция worker должна гарантировать общий результат всех запрошенных свойств; один progress нельзя сохранять как достоверный общий успех.
