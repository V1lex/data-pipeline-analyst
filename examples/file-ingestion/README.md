# Пример преподавателя: приёмка файла

В серверном API реализован отдельный фиксированный демонстрационный сценарий. При первом обращении интеграция передаёт технический ID, ID загруженного файла и хотя бы одно правило. Приложение проверяет каждую строку: поддерживаются непустое значение, уникальность, числовой тип, сравнения с числом, дата в формате YYYY-MM-DD и принадлежность заданному списку строк. Пустой файл считается ошибочным. Результат и пройденный путь записываются в БД проекта и возвращаются в ответе API. Для повторного обращения можно передать тот же ID без файла. Этот сценарий не запускается автоматически при прикреплении файла в чат.

## Демонстрация в чате

Прикрепите `orders_quality.csv` и напишите: `Проверь: order_id уникален, quantity положительное, price неотрицательная, order_date корректная дата, city не пустой`. Программа выполнит пять явно названных проверок по всем строкам, передаст факты агенту и укажет примеры нарушений. В третьей строке есть повторный ID, нулевое количество, отрицательная цена, некорректная дата и пустой город.

Чат распознаёт ограниченные формулировки: имя колонки непосредственно перед условием, например `price больше 0`, `quantity не меньше 1`, `id уникален`, `city не пустой`, `price числовой`, `order_date корректная дата`. Это не универсальное понимание любых бизнес-правил; агент должен сообщать только о фактически выполненных проверках. По общему запросу о пропусках проверяются распознанные колонки. За запрос проверяются не более трёх файлов; для JSON/JSONL колонки обнаруживаются по профилю первых 1000 записей. Для других формулировок и сложных правил автоматическая проверка не гарантируется.

## Пример интеграционного сообщения

После создания проекта и загрузки источника можно отправить запрос `POST /api/v1/projects/{project_id}/file-ingestions` с телом:

```json
{
  "technical_id": "file-001",
  "source_id": "UUID-загруженного-файла",
  "request_id": "UUID-запроса",
  "rules": [
    {"kind": "unique", "column": "order_id"},
    {"kind": "gt", "column": "quantity", "value": 0},
    {"kind": "gte", "column": "price", "value": 0},
    {"kind": "date", "column": "order_date"},
    {"kind": "not_null", "column": "city"},
    {"kind": "one_of", "column": "status", "values": ["paid", "pending"]}
  ]
}
```

Также доступны `number`, `lt`, `lte`. Числовые сравнения требуют конечное число. Пустые значения другие правила пропускают; если пустота недопустима, добавьте `not_null`. Уникальность проверяется среди непустых значений. Ошибки содержат количество и до десяти номеров записей данных на правило; для CSV заголовок не считается записью. Неизвестные правила и колонки не считаются успешной проверкой. Повтор того же `request_id` с другими правилами отклоняется.

По условию примера повторный ID сразу получает статус успеха, даже если исходная проверка завершилась ошибкой: такой статус означает, что файл уже загружался, а не что его данные корректны. Ответ API содержит предыдущий результат проверки. Новый файл с тем же ID, но другим содержимым, отклоняется как конфликт. Транспорт внешних уведомлений в примере не задан: статус хранится локально и доступен через API, но наружу не отправляется.

Это не конструктор произвольных процессов и не выполнение PySpark-кода. Загрузка файла в диалог и приёмка по техническому ID — отдельные действия. Для интеграции с внешней системой нужны её протокол, адрес и бизнес-правила, которых в примере нет.

`model.json` — формальная абстракция этого сценария для TLC. Её можно проверить через `PYTHONPATH=backend/src python -m compiler.formal_check.src.main examples/file-ingestion/model.json --timeout 60` при установленных Java и `TLC_JAR_PATH`. Проверяются достижимость трёх итогов, отсутствие проверки на ветке повтора и отсутствие ошибок до проверки. Проверка абстрактной модели сама по себе не доказывает корректность реализации Python; её поведение дополнительно проверяется тестами.
